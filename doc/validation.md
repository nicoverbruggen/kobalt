# Native validation

Use a prepared native Qt 6.11 or newer Qt 6 SDK. Configure once as described in [Building](building.md). The examples below use Mac; Linux has corresponding `linux` presets. Desktop defaults to sensorless orientation. Enable `KOBALT_DESKTOP_SENSORS` for sensor lock/debounce and borrowed-sensor handoff checks; the default suite retains manual rotation and sensorless lifecycle assertions. Run the commands below from `platforms/desktop/`. They use this checkout's code, assets and incremental cache. No device, firmware, Python or private service is required.

This file holds the everyday commands, the guards, the test inventory, the book fixtures and the feature coverage with its gaps. The detail for each feature area is in its own file under `doc/validation/`, listed in [Area checks](#area-checks).

## Validation guard

The full native suite, the full gallery and Kobo packages take minutes. A pass stays valid until a build-relevant file changes. `platforms/validation-record.cmake` records passes and reports them.

To run the full native suite and record a pass, run this from the repository root:

```sh
cmake -DPRESET=mac -P platforms/validation-record.cmake
```

It builds `mac-tests`, runs `ctest --preset mac` and records the run if it passes. It exits with the status of the step that failed. Use `-DPRESET=linux` on Linux. Add `-DARGS="-L;model"` to run and record that selection instead. `-DJUNIT=<file>` also writes a JUnit report. A plain `ctest --preset mac` run is not recorded, because CTest has no step that runs after its results are known. The launcher's full-suite action and the release profile of [Release evaluation](release-evaluation.md) run the full suite through this command, so their passes count. The full `screenshots` target records itself when a complete capture finishes. Captures filtered with `KOBALT_GALLERY_SCENE` or `KOBALT_GALLERY_CASE` are not recorded. `platforms/kobo/build.sh` records each package that it builds, with its target, logging choice and explicit `KOBALT_RELEASE_VERSION`. A publication build, which sets `KOBALT_RELEASE_VERSION`, also records its commit, because the package shows it. A validation build does not, so a new commit of the same sources does not need a new package. `--check` builds are not recorded.

A record contains the run, its options, a tree hash and the time. Native records distinguish `variants=representative` (the default) from `variants=all` (`KOBALT_TEST_ALL_VARIANTS=1`). Both records can exist for the same tree. A representative pass does not satisfy an all-variant check or block its run. Old native records without a variant mode prove neither mode. The tree hash covers tracked files and untracked files that Git does not ignore. It leaves out `doc/`, all other Markdown files, `.claude/` and `build/`. The same content gives the same hash whether it is committed, staged or only in the working tree. If a file changes while the run is in progress, the run is not recorded. Records stay in `build/validation/` of the worktree that ran.

To see whether the current tree passed a run, use `cmake -DMODE=check -DRUN=ctest:mac -P platforms/validation-record.cmake`. Prefix that command with `KOBALT_TEST_ALL_VARIANTS=1` to check release coverage. Other run names are `gallery:mac`, `kobo:qt5` and the other Kobo targets. `-DMODE=hash` prints the tree hash.

An optional local Claude Code hook can call `cmake -DMODE=hook -P platforms/validation-record.cmake` before each Bash command. Keep its configuration in the ignored `.claude/` directory; the repository does not install the hook. It refuses a full `ctest --preset mac` or `linux`, the recording command above, a full gallery build and a Kobo package build when the record shows that this tree already passed. Its message names focused label runs instead. To run one anyway, put `KOBALT_REVALIDATE=1` before the command. Runs with `-L`, `-R`, `-E`, `-N` or another test selection, filtered galleries, `--check` builds and the launcher's own tests always proceed. The hook allows a command that it cannot read with certainty, and a run whose output directory is missing.

## Main-thread guard

Normal diagnostics retain events in worker-written batches without a sync for an activity-only batch. A warning, an error or a lifecycle flush requests a sync. JSON serialization runs on the logging thread. Only detailed mode writes memory samples and expensive timing fields to the log. Normal mode still takes one resource sample per written batch on the logging thread. The sample refreshes the crash report's resource snapshot and raises a `memory-pressure` warning when less than 16 MiB is available, at most once a minute. In normal mode, a batch of routine activity is written 30 seconds after the last event, and at most 60 seconds after the first. Warnings, errors and detailed mode keep a one-second quiet time and a five-second maximum. Sleep, close, USB and power-off flush at once. These targets hold while the writer is available; worker stalls, failed writes and power-loss durability have no such bound. Normal allowed-wait events report operations lasting at least 50 ms, with their reason and duration. Detailed mode reports all measured waits.

`src/support/main_thread.h` enforces the rule that a page turn never waits for storage. The reader registers itself as an interactive screen while a tap can turn the page. Each operation that writes storage or waits for another thread reports itself: profile database calls, synchronous record writes and flushes, JSON, bookmark, highlight, layout-cache, sleep-snapshot, dictionary and annotation-export files, and on Kobo, Nickel progress and reading-time writes. When such an operation runs on the main thread while the reader is interactive, that is a violation, unless an `AllowBlocking` scope names a reason. Sleep and host checkpoints are such scopes. Known exceptions, each marked with `AllowBlocking`: the Android and desktop library still saves, reads book progress and prepares an opening on the main thread, also while a book is open. On Android and desktop, the host checkpoint after a book opens waits on the main thread. On Kobo, opening attempts only a native status update under the loading view, before input is enabled. It does not save or read back position, percentage or estimates, and it does not retry. Firmware 4.46.23836 and 6.0.279225 status-update disassembly leaves `DateLastRead` untouched. Full native progress writes remain at lifecycle boundaries. Most settings changes, including a dictionary choice and a KOSync sign-in or account setting, wait for their write, so the caller can undo the change when the write fails. Dark-mode changes save on the profile writer thread and publish the new mode after a successful save. Annotation lists, the annotation editor and annotation export read saved rows on the main thread when the user opens them, and export writes its file there. The settings and annotation exceptions run when the user changes a setting or opens a panel, not on a page turn. The desktop and Android opening checkpoint can run while the user reads; it remains open work. On Kobo, `wifi-off` is a reported violation, not an exception: when a KOSync sync that turned Wi-Fi on ends while the reader takes input, Nickel's `WirelessManager::off()` runs `killall dhcpcd` on firmware 4.46.23836 and waits for it on the main thread. This happens at the end of a sync while reading or of a wake sync, at Skip, and at the end of an opening sync that outlasts the loading screen. The event log records `main-thread-blocked` once and a `main-thread-wait` with the duration of each call. A Clara BW measured about 87 ms, and the wait stays reported. When such a sync ends at sleep, at wake before the reader is shown or at close, the wait runs under the `wifi-off at sleep` or `wifi-off while closing` scope below. The Wi-Fi power saver also turns Wi-Fi off through Nickel, under the `wifi-off before reader input` or `wifi-off at sleep` scope, so its wait is an exception and not a violation. Both calls still record a `main-thread-wait` with their duration. The test executables check only work that runs inside event delivery, so a test can inspect saved data between events.

The reader also names these lifecycle scopes explicitly:

- `closing reader`: the reader is being destroyed and cannot accept input. Its destructor persists the informational KOSync timestamp and requests a diagnostic flush bounded to one second.
- `opening status before reader input`: the loading view still owns presentation. Nickel's interface-thread API attempts the status-only update once before the reader accepts input.
- `remembered layout before reader input`: the reader window is still being built. When the opened book's layout, margins or screen density differ from the last layout remembered in the shared settings, `reader-settings.json` is written, so the reader starts from settings that are on disk.
- `wifi-off before reader input`: the opened book is not presented yet. With the Wi-Fi power saver on, Nickel's `WirelessWorkflowManager::turnWifiOff()` waits for `killall dhcpcd` on firmware 4.46.23836, and for four child processes on firmware 6.0.279225, before the reader accepts input. Nickel offers no call that hands the whole shutdown to a worker.
- `wifi-off at sleep`: the reader is hidden for sleep, or wake has not shown it yet. The Wi-Fi power saver's `turnWifiOff()`, or `WirelessManager::off()` for Wi-Fi that a cancelled or finished KOSync sync turned on, waits for the same child processes.
- `wifi-off while closing`: the reader is closing and takes no input. `WirelessManager::off()` turns off Wi-Fi that a cancelled or finished KOSync sync turned on.
- `final native progress before storage handoff`: USB or shutdown has stopped reader input and drained pending storage work. Nickel's interface-thread API writes and verifies the final native progress before the handoff continues.

These scopes permit waits only at their lifecycle boundaries. They do not permit storage waits during reading. The opening status scope replaces the old native opening-progress write and its retries while reading.

The native tests run with `KOBALT_STRICT_MAIN_THREAD=1`, set by `platforms/desktop/run-test.cmake`. A violation aborts the test and names the operation. To list every violation with its call stack, run the tests with `KOBALT_STRICT_MAIN_THREAD=trace`, for example `KOBALT_STRICT_MAIN_THREAD=trace ctest --preset mac -R lifecycle --output-on-failure -V`. Trace mode logs each distinct stack once and lets the test continue. On Kobo, a violation adds one `main-thread-blocked` event per operation to the event log. `model.main-thread` checks the guard itself.

Diagnostic event writes run on their own thread. `flushDiagnostics()` waits for that worker and calls the main-thread guard; reader callers must be at a lifecycle boundary. Tests that read `events.jsonl` call it first.

## Page-turn diagnostics

Kobo builds can log input, render, display-flush and standby events that explain a delayed or doubled page turn. Verbose logging is opt-in at startup through `.adds/kobalt/diagnostics-enabled` or `KOBALT_DIAGNOSTICS=1`, and direct Kobo builds and diagnostic packages enable it automatically. [Page-turn diagnostics](validation/diagnostics.md#page-turn-diagnostics) describes the events and their limits, the Qt5 standby input guard and how to collect a report.

The book is checked in, so testing needs no download or another checkout. Screenshots include the book's cover and narrative text. ## Temporary files and timing

Shared native fixtures verify their immutable staged asset bundle once when constructing reading-font inputs. Model matrices reuse those paths without retaining font bytes or open files. Desktop rows also reuse the placeholder font registration, while each profile supplies its own optional sideload directory. Asset mutation and recovery checks use separate bundles and retain production verification on every requested check.

All native checks and screenshot runs use private working and temporary directories under `build/desktop-mac/test-tmp/`. The CMake parent removes those directories after success, failure, signal termination or its timeout: 30 seconds for fast checks, 120 seconds for integration checks and 300 seconds for the full screenshot run. Regression children have a 90-second guard. CTest leaves five seconds after the launcher guard for cleanup. These process budgets detect hangs; they do not change per-action assertions or USB deadlines. Desktop fixtures drain the reader before removing their profiles. Screenshot staging stays inside the parent-owned temporary directory. If replacing a complete screenshot set fails and rollback also fails, the previous set remains outside that directory and the error names its location. Keep the current screenshot set, latest useful failure evidence and incremental caches.

Timing method and measurements are in [Performance and evaluation](validation/evaluation.md).
