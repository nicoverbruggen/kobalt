# Diagnostics checks

Label `diagnostics`. Build `mac-tests`, then run `ctest --preset mac -L diagnostics` from `platforms/desktop/`. `ctest --preset mac -N -L diagnostics` lists its tests.

These checks cover the diagnostic log, its batches and limits, descriptor-exhaustion reports, crash reports, the storage diagnostics in the desktop app and the Kobo standby input guard and diagnostics. `platform.standby-input` and `platform.standby-diagnostics` run the Kobo standby code with injected reads, writes and hooks, in processes with and without verbose diagnostics. [Page-turn diagnostics](#page-turn-diagnostics) describes the events that these checks protect.

## Crash reports

`model.crash-reports` crashes child processes. Register capture and stack scanning for ARM Linux run only on a Kobo, so read a report on a device after a crash to check them. On Linux, software-generated signals record the sender PID and UID, and synchronous faults record the fault address. Reports cannot capture `SIGKILL`.

## Page-turn diagnostics

CI release builds keep verbose logging off by default. It is opt-in at startup through `.adds/kobalt/diagnostics-enabled` or `KOBALT_DIAGNOSTICS=1`. Direct Kobo builds and diagnostic packages enable it automatically. Builds with verbose logging off do not collect the extra input and operation events. Normal `diagnostics/events.jsonl` and `.previous` files are limited to 128 KiB each. Verbose logs keep the current file and five older files, limited to 16 MiB each (96 MiB total), with the same 128 KiB worker batch size. The older files are `events.jsonl.previous`, then `.previous.2` through `.previous.5`, from newest to oldest. `diagnostics/session-context.json` preserves the latest verbose startup/build and power-observer capabilities independently of event rotation. These files contain no input text or SQL values. Logs use UTC and monotonic milliseconds. Linux also records `boot_ms`, a suspend-inclusive clock. Thread identifiers and `main_thread` distinguish GUI work from worker work. CPU frequency, when available, is sampled on the logging worker with its own `sample_monotonic_ms`; it is not the frequency at the original tap.

`input-event` records input source timestamps and whether delivery is spontaneous. Event propagation can produce several entries for one contact. `page-turn-input` records the accepted or rejected navigation, its source press time, direction, page and busy state. Page-turn gestures less than 200 ms after the last accepted navigation are ignored. Source timestamps preserve that interval when GUI work delays delivery; timestamp-free inputs use elapsed delivery time. Ignored gestures do not extend the window. This filter does not cancel a genuine later retry or diagnose an initial stall.

`render-queued`, `render-start`, `render-end`, `frame-ready`, `page-paint-start` and `page-turn-painted` trace a render through the worker and GUI. Normal logging, as in release builds, records only failed renders and failed page animations; `full-flash`, successful `page-animation` results and successful `render-end` lines need detailed diagnostics. Their `render_id` joins the stages. `page-turn-buffered` identifies the existing one-turn queue. `operation-start` and `operation-end` share an `operation_id` and name; an unfinished start can identify work still running when a trace stops. These cover guarded JSON/file work and waits, profile write transactions, background writes, native progress and reading-time writes, native session flushes and display flushes. A transaction span can include a rollback and is not a success report. Existing result events retain save and render failures.

`standby-request` and `standby-resumed` observe Nickel's power-manager signals, separately from the sleep-screen workflow's `sleep-start` and `sleep-end`. `power-observer` reports the available signals and optional native suspend hooks. Native suspend operation spans bracket `suspendDevice` and `suspendDeviceWithAlarm`; entry means a suspend call was attempted, not proof the kernel suspended. Clock differences can corroborate time spent suspended. These events do not report every CPU frequency transition.

Display-flush spans end when the native flush returns. This does not establish universal physical panel completion. A successful supported animation emits `display-complete` after its final driver completion wait. Ordinary and passthrough refreshes keep their native behavior. Input delivery timestamps are not physical sensor timestamps unless the platform supplies them.

On Qt5, reader standby also checks input immediately before Nickel writes `mem` to `/sys/power/state`. The check applies only inside a native suspend call while Kobalt has a visible, active reader. It defers that attempt if touch acquisition advanced during preparation, if touch, mouse, key or wheel input is queued in Qt, or if touch acquisition occurred within the last 200 ms. That short acquisition window covers the gap before the driver queues the event; it adds no polling timer. The guard leaves input queued and lets Nickel finish its normal cleanup. It does not replace Nickel's wakeup-count handshake, change the navigation filter, or guard stock reader and sleep-screen suspension. `power-observer.kernel_input_guard` reports the write hook and suspend wrapper, not verified late-input cancellation. If either hook is missing, native behavior remains. If the raw-read hook is missing, the guard keeps the pre-write input checks and allows the native write when input is quiet; a mapping hook can be bypassed by another mod.

`standby-preparation` records the outer native call, whether the reader guard is active, and whether Nickel supplied a numeric saved wakeup count. `standby-wakeup-check` records Nickel's write to `/sys/power/wakeup_count`, including the supplied counter, result and error number. An absent count in the preparation event shows that Nickel can bypass this handshake. These helper events observe Nickel’s existing writes. The separate evidence sampler never reads `/sys/power/wakeup_count`. `input-acquired` records Qt5 acquisition before GUI delivery, with a sequence number, a `touch-read` or `touch-map` stage and no coordinates. A read and its later mapping can each advance this sequence; it is not a contact count. `standby-input-check` records the preparation baseline and queued-input state. `standby-deferred` records the final veto reason. The `kernel-suspend` operation brackets the check and possible state write, so its start alone does not prove suspension was attempted. `kernel-suspend-result` reports Nickel’s helper result and error number after the call returns. Treat `power-write` as the kernel write result: Nickel’s helper can report success after a short write or a failed retry. Within the hooked native call, count-check and sleep-write tracing also cover attempts outside the reader guard, including sleep-screen suspension. These are user-space boundaries, not kernel tracepoints or a verified wakeup-IRQ report. Boot-clock differences across the operation can corroborate actual suspension. Hardware validation must still establish that the guard catches the reported race and that normal standby resumes afterward.

The Qt5 and Qt6 suspend diagnostics add an optional hook for the `write` import in Qt Core. It is active only on the thread inside the observed native power helper. `power-write` records the raw byte count, return value, failure errno and monotonic/boot clocks immediately around the libc call. It preserves arguments, return values and errno, including short writes and `EINTR`; it adds no retry. `fd_path_verified` means `/proc/self/fd` identified the expected sysfs path. A false value must not be treated as proof of a suspend write. Records are buffered in fixed thread-local storage and queued after the helper returns. A hang or power loss before return loses those records. `power-write-observation` reports hook availability, captured calls and calls omitted beyond the per-helper limit. No observed call is an instrumentation gap, not proof of a successful or skipped suspend. These remain libc boundaries, not kernel tracepoints. Qt6 uses an observation-only power-helper hook. It never applies the Qt5 input guard. The raw read and write hooks are optional on both firmware lines; `standby-diagnostic-capabilities` reports their installation and the power-helper hook separately.

`input-driver-read` independently observes successful `read` calls in the firmware touchscreen plugin, before coordinate mapping and GUI delivery. It reports the byte count, descriptor, verified input-device name, monotonic/boot clocks around the read hook, and power-write attempts active at entry and return. It does not collect input payloads or coordinates or retry reads. On Qt5, every successful read in this touchscreen plugin advances the input guard before diagnostic allocation or descriptor inspection, including when diagnostics are disabled. Qt6 remains observation-only. Empty and failed reads pass through without an event. This probe remains useful when another mod replaces the mapping hook and `input-acquired` disappears. Its diagnostic sequence is independent of the guard acquisition sequence. `standby-diagnostic-capabilities.touch_read_hook` reports installation, while actual read events prove execution. On Qt5, exit clocks follow kernel wake registration; `read_exit_after_wake_request` identifies that added work. Neither probe supplies a physical sensor timestamp.

The `attempt` field joins preparation, helper results, raw writes and evidence samples. `input-acquired.power_write_attempt` identifies a write active at the mapping hook; zero means no observed write was active. It does not identify a physical sensor timestamp. The Qt5 mitigation keeps the native wakeup-count handshake and navigation filter. Qt6 diagnostics do not install this mitigation.

On Qt5, late-input cancellation requires a successful numeric wakeup-count write in the same outer attempt. A preparation argument alone does not arm it, and each native `mem` call consumes it. Immediately before the final input check, the guard publishes a cancellation attempt to the input thread. Late acquisition requests `kobalt-input 1000000000` through `/sys/power/wake_lock` before diagnostic work. This one-second timeout uses kernel nanoseconds. The request expires automatically; there is no untimed lock, explicit unlock or idle polling timer. Expiry advances the kernel wakeup count, so the event can still cancel an armed suspend after the timeout. `standby-input-wake-request` records the attempt, acquisition sequence, stage, timeout, result, errno and completion time. The file descriptor is opened before the final guard and retained until process exit. Late acquisition writes through this descriptor before sampling clocks or allocating diagnostic records. These records are distinct from sampled `standby-input-wakeup` counters.

Missing or failed count checks, missing raw-read hooks and an unavailable wake-lock file fall back to the pre-write input checks and then allow Nickel’s native write. A failed late request disables only the cancellation bridge until Nickel restarts. Only queued input, acquisition during preparation, acquisition still in progress or acquisition within the quiet window defer reader standby with `EAGAIN`. Stock sleep-screen suspension is unchanged. Opening the file proves availability only. Permission, allocation or lock-count failures can still occur on the first write, and that failure cannot cancel a syscall already in progress. The syscall count and timeout are bounded, but kernel mutexes and allocation can delay the request. Userspace may also freeze before it registers the event. Hardware validation must establish cancellation and later quiet standby; the mitigation does not guarantee closure of the kernel IRQ/freezer race.

Normal logging also records bounded Qt5 guard evidence without the verbose marker. `standby-input-capabilities` records the read hook, wake-lock probe errno and successful numeric handshake state on the first protected attempt. `standby-input-fallback` records each change of fallback reason or errno, including recovery to `none`; `previous_reason` and `attempts_since_last_event` describe the preceding state and its attempt count. Repeated attempts in the same state add no events. `standby-input-wake-failure` records the first request failure. `standby-input-wake-result` is written only when requests started during that protected call. It records their count and Nickel’s helper result and errno at native return. Input threads increment an atomic counter; the GUI thread queues these records to the existing async writer. A request can finish after native return; its first error is then recorded at a later protected check. If an input thread reads the active attempt before native return clears it but increments the request counter after the return summary samples it, that request is omitted from the count. This is a diagnostic undercount only; any failure remains available to log at a later protected check. These normal events do not log each tap. USB’s diagnostic pause still suppresses all logging.

At startup, `standby-input-device` records each input event device’s name, event/absolute capabilities, parent driver and wakeup setting when available. It excludes serial, `phys` and `uniq` fields. `session-context.json` retains the driver inventory, hook capabilities and source commit/modified state across event rotation. Driver identity is evidence to inspect, not a hard-coded assumption about the touchscreen.

At startup, native preparation and native return, a bounded worker sample reads wakeup-source counters, `pm_wakeup_irq` and suspend statistics. It also reads the kernel log without clearing it, retaining only PM, freeze, task-restart and resume-IRQ messages. The filter handles standard printk headers and MediaTek CPU/task prefixes, including the dot prefix captured on Clara BW and the shorter prefix during console suspension. The captured suspend, resume and task-restart lines are regression fixtures. It retains device suspend failures. `standby-kernel-log` reports lines examined, oversized lines, matched messages and candidate lines rejected by the filter. `standby-kernel-rejected` captures only the latest eight rejected PM candidates per sample. Each record keeps at most 256 bytes of the original line and a hex copy of its first 64 bytes, plus the original length, truncation flag and rejection reason. This exposes unknown prefixes and control bytes without collecting the full kernel log. The summary reports captured and omitted candidate counts and whether the prefix expression is valid. Rejected candidates are diagnostic evidence, not confirmed PM messages. Samples can repeat kernel messages; use their original kernel timestamps. The reads never enable debugfs, change kernel settings or read the potentially blocking wakeup-count handshake. Errors, unavailable files, malformed headers and truncated samples are explicit. A missing source or IRQ report does not prove that a wakeup did not happen. The filter also retains active and last-active wakeup-source messages and IRQ-list overflow messages from the Sage/Elipsa kernels. Android-style `last_resume_reason` and `last_suspend_time` files are sampled when available, with the same byte limits and error reporting.

`standby-kernel-capabilities` records the kernel release, debugfs mount status and clock availability and survives event rotation in `session-context.json`. The sampler accepts both the older `hit_count` and newer `wakeup_count` table layouts without renaming either counter. When the wakeup table is missing, unreadable or malformed, `standby-input-wakeup` samples bounded power counters from each input device’s nearest counter-bearing parent. It reports missing, malformed and truncated counters. The scope is explicitly kernel-dependent: some 2.6 kernels return the same global count through every device path, so these values do not prove that a particular device caused a wakeup. Sampling never mounts debugfs or changes power settings.

If `CLOCK_BOOTTIME` is unavailable, boot fields remain `-1` and the records include `*_realtime_ms` as an approximate fallback. Realtime fields are `-1` when the boot clock is available. Wall-clock adjustments can change these differences, so do not present them as exact sleep durations. Monotonic time alone excludes suspension on the inspected kernels.

`descriptor-exhaustion` is logged as an error in every build when a call that Kobalt makes runs out of file descriptors (`EMFILE` or `ENFILE`): profile database opens, writes and commits, JSON records, book archives, bundled assets and Nickel's database on Kobo. A KOSync transport failure checks by opening `/dev/null` at that moment, because Qt opens network sockets on its own thread. The event lists the open descriptors of the process: the total, files, sockets, pipes, inotify instances and other kinds, and the five most opened files with their counts. System files, mod folders such as Kobalt's profile on Kobo and the files directly in Nickel's `.kobo` folder keep their path. Any other file, including store books under `.kobo/kepub` and imported books on Android, is named by its extension only, so book paths and store IDs stay out of the log. On macOS only the total is reported, because its descriptor list has no link targets. `listed` is false when the list could not be read. The event runs at most once a minute and leaves `errno` unchanged. One descriptor is kept in reserve: the listing and the log write each borrow its slot and take it back at once, so the report works and reaches the log when no descriptors are left. It only sees failures in Kobalt's own calls, not in Nickel's.

Evidence samples run on the logging worker. Compare their actual `sample_monotonic_ms` and `sample_boot_ms` with the request clocks and raw write clocks. File evidence and kernel-log reads include `read_enter_*` and `read_exit_*` clocks to expose a read that spans suspension. Kernel-log reads report the byte limit and unknown completeness: `READ_ALL` drops whole records to fit, so a short read does not prove a complete log. A sample requested at preparation can execute after wake; its phase is a request label, not a guaranteed pre-suspend boundary. At most four samples can wait; `standby-evidence-skipped` reports excess requests. Sampling and logging can affect scheduling and storage timing, so compare positive reproductions and do not interpret a negative run as proof of a fix. The native standby checks do not validate a real firmware hook or physical wakeup.

For a reporter run, install the matching Qt5 or Qt6 diagnostic ZIP and confirm the diagnostic version in About. Read normally until the delayed or doubled turn occurs, then note the approximate time and whether a retry tap was needed. Save the diagnostics promptly through the existing report flow, including all rotated event files and `session-context.json`. Include one deliberate sleep/wake check and a later quiet reading interval to compare stock sleep-screen suspension and reader standby. The Qt5 package includes the late-input mitigation and its failure evidence; the Qt6 package remains diagnostic-only.

The caller enqueues small records. JSON formatting, memory/frequency sampling and batched file writes run on the diagnostic worker. Diagnostic state and session JSON reports use background writers. No diagnostic polling timer or per-tap storage sync is added. Warnings, errors and lifecycle flushes retain the existing durability policy. Detailed logging still has allocation and scheduling cost, and a queue overflow or failed write can lose events; a negative reproduction is not proof of healthy hardware timing.
